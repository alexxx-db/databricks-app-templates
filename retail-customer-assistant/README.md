# Retail customer assistant

A customer-service console for an online retailer: an AI assistant that looks up customers and orders, checks return eligibility and files returns through governed tools, plus Customer 360 and Operations views over the same data.

| | |
|---|---|
| Stack | Streamlit app, Unity Catalog tables, SQL warehouse, Model Serving (tool calling), Lakeflow Job |
| Data | Synthetic: 800 customers, 87 products, 4,000 orders, returns, store policies (generated by the setup job) |
| Runs as | App service principal |

## What it shows

**Assistant tab.** A tool-calling agent loop (`assistant.py`) over seven tools: `find_customer`, `list_recent_orders`, `get_order`, `check_return_eligibility`, `create_return_request`, `search_products`, `get_policy`. Every tool call is shown under the reply, so you can see exactly what data the answer came from.

- **Policy lives in code, not the prompt.** Return eligibility (30-day window, 60 for Gold, final-sale exclusions, one return per order) is a pure Python function. `create_return_request` re-checks it before writing, so the model can't talk its way into an ineligible return.
- **All SQL is parameterized.** User and model text are bound parameters, never pasted into SQL.
- **Least privilege.** The app's service principal can read the schema and write only to `returns`.

**Customer 360 tab.** Look up a customer by email: profile, orders, line items, and the same eligibility verdict the agent uses.

**Operations tab.** 30-day orders and revenue, open return requests, return rate by category, late deliveries.

## Deploy

Prerequisites: a SQL warehouse, an existing catalog you can create schemas in, and a chat model endpoint that supports tool calling (default: `databricks-meta-llama-3-3-70b-instruct`).

```bash
cd retail-customer-assistant
databricks bundle deploy -t dev --var sql_warehouse_id=<warehouse-id>
databricks bundle run setup -t dev   # create <catalog>.<schema>, generate data, grant the app access
databricks bundle run app -t dev     # start the app
```

The setup job writes to `main.retail_assistant` by default. To use another location, pass `--var catalog=<catalog> --var schema=<schema>` **and** set `RETAIL_SCHEMA` in `app.yaml` to the same `<catalog>.<schema>`. Rerunning the setup job regenerates all tables (dates are relative to the day it runs).

The setup job grants the app's service principal `USE CATALOG`, `USE SCHEMA` + `SELECT` on the schema, and `MODIFY` on `returns`. If you load data another way, run those grants yourself (see [resources and permissions](../docs/resources-and-permissions.md)).

## Try it

Open the app, copy any email from **Customer 360** (or run `SELECT email FROM main.retail_assistant.customers LIMIT 5`), then ask the assistant:

- *I'm `<email>`. Where is my latest order?*
- *Can I return it?* → the agent checks eligibility and asks you to confirm before filing.
- *What's your shipping policy?*
- *Show me tents under $200.*

## Make it yours

| To change | Edit |
|---|---|
| Return rules | `return_eligibility()` in `assistant.py` (and the `returns` policy text in `setup/generate_data.py`) |
| Agent behavior | `SYSTEM_PROMPT` in `assistant.py` |
| Add a tool | A method on `Tools` + an entry in `TOOL_SPECS` |
| Use real data | Point `RETAIL_SCHEMA` at tables with the same columns, or adapt the SQL in `Tools` |
| Model | `--var serving_endpoint_name=<endpoint>` |

For production, consider moving the agent into its own serving endpoint (see `agent-openai-agents-sdk`) so it gets MLflow tracing, evaluation and independent scaling, and keep this app as the UI.

## Testing

The tests build the generated data in local Spark (ANSI mode, like Databricks SQL), then run the tools, the agent loop (with a scripted model) and the real `app.py`. Spark executes every query the app sends, so SQL errors fail the test. Needs Java 17+.

```bash
uv run --no-project --with "pyspark~=4.0" --with pytest --with-requirements requirements.txt pytest tests -q
```
